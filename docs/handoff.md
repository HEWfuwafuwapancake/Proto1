## 2. 次にやること：No.50 の段階1（プラン。管理者の確認待ち）

下のプランを管理者に確認してもらう。確認が取れたら、段階2・3 のプロンプトをここに書く（実装は【当面】のとおり Codex）。No.50 が終わったら No.19 の段階1。作業ブランチは `feature/auto-delay-steady`（プランだけ push 済み）。

### ねらい

Tailscale の2人対戦で、ゲームの ping はふだん30ms以下なのに、自動の delay が **9**（押してから動くまで約0.15秒）になった。ふだんの ping なら **4**（約0.07秒）で足りる。
今は「試合開始前の2秒で、いちばん遅かった1回の ping」から決めているので、一瞬だけ遅れた1回（約100ms）で delay が大きくなる。**たまにの遅れに引っぱられず、ふだんの ping に合った delay にする。**
No.49 で「4人で delay 3 は止まった」ので、遅くなりやすい回線ではちゃんと大きくなることは残す。

### 原因（コードを読んで分かったこと）

1. `SessionCalc::GetPeakPing`（`src/net/sessioncalc.cpp`）が、2秒の中の**最大値**を使っている。60回/秒測るので、2秒で約120回のうち1回だけ遅くても、それで決まる。
2. ping は「相手が最後に受け取った自分の時刻（`Echo`）」を返してもらって測る（`ReceiveMonitor`）。相手が新しいパケットをまだ受け取っていないフレームでは**同じ `Echo` がもう一度返ってくる**ので、そのぶん（1フレーム＝約17ms ずつ）長い往復時間として記録される。回線の遅れではない値が混ざる。

### やること

| 場所 | 変えること |
|---|---|
| `src/net/sessioncalc.h` の「調整用の値」 | `AUTO_DELAY_PING_PERCENTILE = 90` を足す（2秒の ping を小さい順に並べ、90% の位置の値を使う。遅いほうの1割は無視する）。`AUTO_DELAY_PING_WINDOW` のコメントを「この間の 90% の値を使う」に直す。`AUTO_DELAY_MARGIN = 2`・`AUTO_DELAY_MIN = 3`・`AUTO_DELAY_MAX = 20` は変えない |
| `SessionCalc::ReceiveMonitor` | `Echo` が前に記録したものと**同じなら記録しない**（`m_LastEcho[peer]` を足す。切断・つなぎ直しで 0 に戻す）。タイトルバーに出す `m_Ping` も同じ扱い |
| `SessionCalc::GetPeakPing` → `GetAutoDelayPing` | 人ごとに、2秒の ping の 90% の値を出し、**いちばん遅い人の値**を返す（4人なら一番遠い人に合わせるのは今と同じ）。記録がなければ -1（今と同じ） |
| `SessionCalcAutoDelay` | 変えない（ping → フレームへ切り上げ ＋ 2） |
| `tests/Proto1Tests/sessioncalc_test.cpp` | 今の `AutoDelay_…` のテストを新しい名前に合わせる。足すのは2つ：①30ms が19回と 100ms が1回 → 使う ping は 30、delay は 4 ／ ②同じ `Echo` が2回届いても、2回目は記録しない |
| `docs/team/04_コマンド一覧.md` | 「直近2秒のいちばん遅い人の ping」を「直近2秒の ping の 90%（たまに遅れた分は除く）の、いちばん遅い人の値」に直す |

- 目安：ping がふだん 30ms なら delay 4、60ms なら 6、100ms なら 8（今の計算と同じ。変わるのは「どの ping を使うか」だけ）。
- 通信の形（パケット・`LOCKSTEP_VERSION`）は変えない。ホストだけが delay を決めて配るので、参加側の版がずれても動きは変わらない（ただしビルド照合があるので、全員同じビルドで遊ぶ）。

### 決めること（おすすめ）

1. **どの値を使うか**：**90%（おすすめ）**／ 75%（delay はもっと小さくなるが、止まりやすい）／ 95%（安全寄り）
2. **同じ `Echo` を記録しない**：**直す（おすすめ）**／ 直さない（遅い値が混ざるが、90% にするだけでもかなり減る）
