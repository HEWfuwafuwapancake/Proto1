# AI の失敗と教訓

AI（Claude と Codex）がミスをして直したときや、ユーザーに間違いを指摘されたときに、1項目ずつ追記していく記録です。
どちらの AI も作業を始める前にこのファイルを読み、自分のミスも相手のミスも繰り返さないようにします
（`CLAUDE.md` / `AGENTS.md` のルール）。相互レビューで見つかったミスも、ミスをした AI がここに書きます。

書き方：新しい項目は下に足す。見出しは「日付 内容」。「書いた AI／起きたこと／原因／次からどうするか」を書く。

---

## 2026-10-19 Python をヒアドキュメントで渡したら日本語と `\n` が崩れた
- **書いた AI**：Claude
- **起きたこと**：ファイルを書き換える Python スクリプトを Git Bash のヒアドキュメント（`python - <<'EOF'`）で渡したところ、
  日本語の検索文字列が一致せずにスクリプトが途中で止まった。また、C++ の文字列に入れるはずの `\n` が本物の改行になり、
  `MessageBox` の文字列が行の途中で切れてビルドが通らなくなった。
- **原因**：ヒアドキュメントで渡すと、文字コードとバックスラッシュがそのまま Python に届くとは限らない。
- **次からどうするか**：日本語やバックスラッシュを含むスクリプトは、Write ツールで scratchpad にファイルとして書き、
  `python -X utf8 <ファイル>` で実行する。書き換えたあとは、変えた行を読んで確かめる。

## 2026-10-19 C++ のファイルに BOM が付かず、ビルドが大量のエラーになった
- **書いた AI**：Claude
- **起きたこと**：Write ツールや Python で書いた `.cpp` / `.h` が BOM なしの UTF-8 になり、
  MSVC が Shift-JIS（CP932）として読んで `C4819` の警告と構文エラーを大量に出した。
- **原因**：Write ツールは BOM を付けない。このプロジェクトは「C++ は BOM付きUTF-8」が決まり（マルチバイト文字セットのため）。
- **次からどうするか**：C++ のファイルを作ったり書き換えたりしたら、ビルドの前に BOM付きUTF-8・CRLF にそろえ、
  `file *.cpp *.h` で確かめる。シェーダー（`.hlsl` / `.hlsli`）は逆に BOM なしにする。

## 2026-10-19 シェーダーの「未初期化の可能性」警告を、変数の初期化だけで消そうとした
- **書いた AI**：Claude
- **起きたこと**：水のピクセルシェーダーで `warning X4000: use of potentially uninitialized variable` が出た。
  変数に初期値を入れても消えず、ビルドをやり直すことになった。
- **原因**：fxc は、関数の途中に `return` が複数あると（特に `[loop]` の中や `out` 引数のある関数）、誤ってこの警告を出す。
- **次からどうするか**：HLSL の関数は出口（`return`）を1つにまとめて書く。ループの中で見つけたら `break` で抜けて、最後に1回だけ返す。

## 2026-10-19 `merge-pr.ps1` が入力を待つことを確かめずに、使えると思い込んでいた
- **書いた AI**：Claude
- **起きたこと**：PR のマージを頼まれたとき、`tools/admin/merge-pr.ps1` をそのまま使うつもりでいたが、
  中で `Read-Host`（「マージしますか？ (y/N)」）を使っており、Claude の実行環境（入力できない）では動かなかった。
- **原因**：スクリプトの中身を読む前に、名前から動きを想像していた。
- **次からどうするか**：`tools/` のスクリプトを初めて実行するときは、先に中身を読み、入力待ち（`Read-Host`）や
  push・ブランチ削除などの外に影響する操作がないかを確かめる。入力待ちがあるときは、同じ確認を自分で行ってから、
  スクリプトが最後に実行するコマンドを使い、そのことをユーザーに伝える。

## 2026-10-20 手順書に「`fetch-latest.ps1` で develop に戻る」と書いたが、マージ前は戻らなかった
- **書いた AI**：Claude
- **起きたこと**：`docs/ai/01_Codexとの相互レビュー.md` のレビュー手順の最後に「`fetch-latest.ps1` で develop に戻る」と書いた。
  PR #17 のレビューで実際に実行したら、フィーチャーブランチのままだった。
- **原因**：`fetch-latest.ps1` が develop に切り替えるのは「マージ済みで GitHub から消えたブランチ」にいるときだけ。
  レビュー中の PR はまだマージされていない。スクリプトの動きを確かめずに手順書に書いていた。
- **次からどうするか**：手順書にスクリプトの使い方を書くときは、そのスクリプトの中身を読んでから書き、できれば書いた手順どおりに一度動かして確かめる。

## 2026-10-20 プロジェクトの外の確認用 C++ でも、BOM なしで書いて同じエラーを出した
- **書いた AI**：Claude
- **起きたこと**：カメラの当たり判定を確かめるために、scratchpad に小さなテスト用の C++（日本語のコメント入り）を Write ツールで書き、
  `cl` でコンパイルしたら、文字コードの読み違いで構文エラーが大量に出た（「C++ のファイルに BOM が付かず…」と同じミス）。
- **原因**：BOM の決まりを「プロジェクトのファイルだけの話」と思っていた。`cl` は BOM がないと CP932 として読むので、どこにある C++ でも同じことが起きる。
- **次からどうするか**：プロジェクトの外で C++ をコンパイルするときは `cl /utf-8` を付ける（プロジェクトのファイルは今まで通り BOM付きUTF-8 にして、`/utf-8` は付けない）。

## 2026-10-20 自分で気づいた「押し出しを高さの制限が取り消す」問題を、確かめずに PR に出した
- **書いた AI**：Claude（見つけたのは Codex のレビュー。必須の指摘）
- **起きたこと**：PR #18（カメラの当たり判定）で、立方体から押し出したあとに地面・水面の高さで y を戻すため、
  押し出しが取り消されて重なったまま残るおそれに自分で気づいていた。しかし PR の「見てほしいところ」に質問として書いただけで出し、
  レビュー後も「推奨くらい」と答えた。Codex は必須と判断し、テストで再現すると実際にカメラが立方体の中に残った。
- **原因**：気づいた不安を、テストで確かめずに相手へ渡した。重さ（必須か推奨か）も、確かめる前に決めていた。
- **次からどうするか**：自分で不具合のおそれに気づいたら、PR を出す前にそれを再現するテストを書いて確かめる。
  再現したら直してから出す。再現しなかったら、そのテストの結果を PR に書く。重さは再現の結果を見てから決める。

## 2026-10-20 `git status` の確認と `start-work.ps1` を1つのコマンドで実行し、他人の未保存の変更を新しいブランチに持ち込んだ
- **書いた AI**：Claude
- **起きたこと**：Doxygen コメントの作業を始めるとき、`git status` と `start-work.ps1` を同じコマンドで続けて実行した。
  develop に `dx11.cpp` の保存していない変更（ユーザーが Visual Studio で入れた空行2つ）があったが、結果を見る前にブランチを作ってしまい、
  その変更が新しいフィーチャーブランチに持ち込まれた。`save-work.ps1` は `git add -A` なので、そのままだと関係ない変更が PR に入るところだった。
- **原因**：状態を確かめる手順と、状態を変える手順を1回にまとめていた。
- **次からどうするか**：作業を始める前は、まず `git status` だけを実行して結果を読む。自分のものではない変更があったら、
  ブランチを作る前にユーザーに伝えて扱いを決める。持ち込んでしまったときは、保存の間だけ `git stash push -- <ファイル>` でよけて、終わったら戻す。

## 2026-10-20 「コメント以外はまったく同じ」と書いたが、確かめ方が空白の違いを無視していた
- **書いた AI**：Claude（見つけたのは Codex のレビュー）
- **起きたこと**：PR #19（ヘッダーに Doxygen コメント）で「コメントを取り除いたコードが、変更前とまったく同じ」と PR に書いた。
  しかし Write ツールで書き直したときに、授業のひな形 `debug_ostream.h` の `#include` の行末の空白が消えていた。
  比べるスクリプトが空白をそろえてから比べていたので、この違いに気づかなかった。動きには影響しない。
- **原因**：確かめ方（空白を無視して比べる）と、PR に書いた言い方（まったく同じ）が合っていなかった。
  また、書き足すだけでよいファイルを Write で丸ごと書き直していた。
- **次からどうするか**：コメントを足すだけのときは、ファイルを丸ごと書き直さず Edit で足す。
  確かめた結果を書くときは、確かめ方のとおりに書く（空白を無視したなら「空白を除いて同じ」と書く）。

## 2026-10-20 Doxygen コメントの説明があいまい・不足していた
- **書いた AI**：Claude（見つけたのは Codex のレビュー。推奨）
- **起きたこと**：`MouseSetLock(bool lock)` を「ロックを切り替える」と書き、指定した状態にする関数だと分かりにくかった。
  また `MATERIAL` / `LIGHT` の `Dummy[3]` にだけメンバーの説明（`///<`）を付けていなかった。
- **原因**：関数名と引数から説明を書き、「切り替え（トグル）」と「設定」の違いを意識していなかった。詰め物のメンバーを説明不要と考えていた。
- **次からどうするか**：bool を受け取る関数は「〜を設定する（true：〜、false：〜）」と書く。構造体はメンバーを1つも残さず説明する。
