## 管理者が決めたこと（このタスクの前提）

- 刀の単押しは No.116 で「ただの斬撃」になっているので、今回は変えない。
- 吹っ飛びは % で増える速さを半分にする（100% のとき今の 50% と同じ速さ）。
- 試合のパラメータは**ホストだけ**が決め、**デバッグ用ウィンドウ**で変える（ゲームの中の設定画面は作らない）。
  SOLO・LOCAL VS ではその PC がホスト。ONLINE の参加側は表示だけ。
- Release の exe でホストが調整するときは `--debugwindow` を付けて起動する（今のまま）。
- 試合の設定は GAME でも DEBUG でも効く。ただし DEBUG の腕の使用回数は今までどおり無制限。

## 進め方（Codex へ。止まらずに上から順に）

1. はじめに `CLAUDE.md`・`AGENTS.md`・このファイルを読み、Notion の開発ログの「タイトル」「要点」「対応モジュール」を読む。
2. 各タスクで次をくり返す。管理者の確認は待たない（このプランが確認済み）。
   1. `.\tools\start-work.ps1 <ブランチ>`（前のタスクのマージ後なので develop の最新から始まる）
   2. プランの「触るファイル」を変える。プランにない大きな変更が要ると分かったら、**止まらずに**一番近い形で作り、
      プランの「実装したこと」と PR に理由を書く（動きそのものを変える判断だけは避け、プランどおりの動きを優先する）。
   3. Debug / Release x64 のビルドが警告 0、`.\tools\run-tests.ps1` と `.\tools\run-tests.ps1 -Release` が全部通る。
   4. 新しい計算のファイル（124 の `tuningcalc`）だけ、わざと壊してテストが落ちることを1回確かめて戻す。
      既存の計算を少し変えただけのタスクはテストが通ればよい。
   5. プランの末尾に「実装したこと」（2〜4行）を書き、`docs/plan/03_新しいアームの仕様.md` の該当の行も直す（腕のタスクだけ）。
   6. `docs/tasks.md` の状態を ✅、PR の番号を書く。`.\tools\save-work.ps1 "No.〇 …"` → `.\tools\submit-pr.ps1`
   7. `gh pr merge <番号> --merge --admin --delete-branch` でマージして、次のタスクへ。
3. ゲームの画面確認・操作の確認はしない（管理者が最後にまとめて遊ぶ）。各プランの「管理者が遊んで確かめること」を、
   最後に `docs/handoff.md` の「次にやること」へ集めて書く。
4. 全部終わったら `docs/handoff.md`（今の状態・次にやること・最終更新：Codex）を書き直し、Notion の No.120〜126 を「完了」と
   PR のリンクにする（書き換えられなければ、最後に管理者へ伝える）。
5. 途中で直せない問題（ビルドやテストがどうしても通らない）が出たら、そのタスクのブランチを `save-work.ps1` で保存し、
   handoff.md の「今の状態」に止まった所と理由を書いて終える。

## 全体の決まり

- 調整する値は各ファイルの上の「調整用の値」に `static constexpr` で置く。プランの数字ははじめの値。
- `src/game` に `g_` 変数や自由関数を足さない。クラスと public なメンバーには Doxygen の日本語コメントを付ける。
- 新しいファイルは No.124 の `src/physics/tuningcalc.h / .cpp` と `tests/Proto1Tests/tuningcalc_test.cpp` だけ（`.vcxproj` と `.filters` に登録する）。
- `core`・`physics`・`net` は `game` を使わない。デバッグ用ウィンドウ（`core`）とゲームの値の受け渡しは `main.cpp` が行う。
