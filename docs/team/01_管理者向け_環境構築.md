# 管理者向け：開発環境の準備とチームの管理

管理者（リーダー＋もう1人）向けの手順。
**Git も Visual Studio も何も入っていない Windows PC** から始める前提で書いてある。すでに入っているものは飛ばしてよい。

| このプロジェクト | |
|---|---|
| 組織名 | `HEWfuwafuwapancake` |
| リポジトリ名 | `Proto1` |
| リポジトリのURL | https://github.com/HEWfuwafuwapancake/Proto1 |

| 自分は… | やる手順 |
|---|---|
| リーダーで、**新しいプロジェクト**（プロトタイプなど）を GitHub に作る | **1 → A → D** |
| 2人目の管理者で、はじめて参加する | **1 → B → D** |
| 管理者で、**別のPC**（家のPCなど）でも作業したい | **1 → C → D** |

---

## 全体像

| 役割 | GitHub での立場 | できること |
|---|---|---|
| 管理者（2人） | 組織（Organization）の **Owner** ＋ リポジトリの **Admin** | すべて。develop / main へのマージ、release / hotfix、メンバー管理 |
| 開発者（メンバー） | リポジトリの **Write**（組織の外部コラボレーター） | `feature/*` での作業と、develop へのプルリクエストまで |

- **Organization が必要な理由**：個人アカウントのリポジトリだと、共同作業者は全員同じ権限になり「管理者2人」を作れない。
- **public にする理由**：無料プランの Organization で Rulesets（ブランチのルール）が効くのは public リポジトリだけ。

ブランチのルールは [03_ブランチ運用ルール.md](03_ブランチ運用ルール.md)、コマンドのまとめは [04_コマンド一覧.md](04_コマンド一覧.md)。

## 1. PC の準備（管理者全員・PCごとに1回）

### 1-0. 用意するもの

- Windows 10 / 11 の PC（管理者としてソフトをインストールできること）
- 空き容量 **30GB 以上**（Visual Studio が大きい）
- メールアドレスとスマホ（GitHub の登録と2段階認証）

### 1-1. PowerShell の使い方

このガイドのコマンドは、すべて **Windows PowerShell** に入力する。

- **開き方**：スタートボタン → 「powershell」と入力 → **Windows PowerShell**（「PowerShell 7」や「コマンドプロンプト」ではない）
- **コマンドの入れ方**：灰色の枠をコピー → PowerShell で **右クリック**（または `Ctrl + V`）→ **Enter**
- ソフトを入れたあとは、PowerShell を **閉じて開き直す**（新しいコマンドが使えるようになる）

### 1-2. GitHub アカウント（まだない人だけ）

1. https://github.com/signup で登録（ユーザー名は英数字）。届いたメールのコードで確認する。
2. 2段階認証：右上のアイコン → **Settings** → **Password and authentication** → **Enable two-factor authentication**。
   スマホの認証アプリで QR コードを読み取り、**リカバリーコードを必ず保存** する。
   （組織の Owner は権限が強いので、管理者は必ず設定する）

### 1-3. Visual Studio 2022

1. https://visualstudio.microsoft.com/ja/downloads/ → **Community 2022** の「無料ダウンロード」。
2. `VisualStudioSetup.exe` を実行（「変更を加えることを許可しますか？」→ **はい**）。
3. ワークロードで **「C++ によるデスクトップ開発」** にチェック。右側の「インストールの詳細」で **Windows 11 SDK** にチェックが入っているか確認（DirectX 11 はこれに入っている）。
4. **インストール**（30分〜1時間）。終わったら一度起動しておく。

### 1-4. Git と GitHub CLI

PowerShell で1行ずつ実行する（「許可しますか？」→ **はい**、「使用条件に同意しますか？」→ `Y`）。

```powershell
winget install --id Git.Git -e --source winget
```

```powershell
winget install --id GitHub.cli -e --source winget
```

`winget` が見つからない場合：Microsoft Store で **「アプリ インストーラー」** を更新する。それでも駄目なら、Git は https://git-scm.com/download/win （全部「Next」でOK）、GitHub CLI は https://cli.github.com/ から入れる。

**PowerShell を閉じて開き直して** 確認：

```powershell
git --version
```

```powershell
gh --version
```

### 1-5. スクリプトの実行を許可する

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

「実行ポリシーを変更しますか？」→ `Y`。

### 1-6. Git の初期設定

`"..."` の中を自分のものに変えて、1行ずつ実行する。

```powershell
git config --global user.name "GitHubのユーザー名"
git config --global user.email "GitHubに登録したメールアドレス"
git config --global core.autocrlf true
git config --global credential.helper manager
git lfs install
```

### 1-7. GitHub にログイン

```powershell
gh auth login --web --git-protocol https
```

8文字のコードが表示される → **Enter** でブラウザが開く → コードを入力 → **Authorize github**。
`✓ Logged in as ...` と出ればOK。

## A. リーダー：新しいプロジェクトを GitHub に作る

### A-1. Organization を作る（チームで1回だけ。もうあれば飛ばす）

1. https://github.com/account/organizations/new?plan=free を開く（右上アイコン → **Your organizations** → **New organization** → **Free** でも同じ）。
2. 入力：
   - **Organization name**：チーム名（例：`HEW2026-TeamA`。URL になる。スペース不可）
   - **Contact email**：自分のメール
   - **This organization belongs to**：**My personal account**
3. 認証パズル・利用規約に同意して **Next**。「Add organization members」は **Skip this step** でよい。

### A-2. Organization の設定（チームで1回だけ）

組織のページ → **Settings** → **Member privileges**：

| 項目 | 設定 | 理由 |
|---|---|---|
| **Base permissions** | `Read` | 組織のメンバーが勝手に書き込めないように |
| **Repository creation** | **Public / Private のチェックを外す** | メンバーが勝手にリポジトリを作らないように |

組織のページ → **Settings** → **Authentication security** → **Require two-factor authentication** にチェック（おすすめ。2段階認証していない人は組織に入れなくなる）。

### A-3. 2人目の管理者を Owner にする（チームで1回だけ）

組織のページ → **People** → **Invite member** → ユーザー名を入力 → Role を **Owner** → **Send invitation**。
相手がメールから承認すると完了。

### A-4. プロジェクトのフォルダを用意する

1. Visual Studio で新しいプロジェクトを作る（例：「空のプロジェクト」C++）。
   場所は `C:\Users\あなたの名前\source\repos`、**「ソリューションとプロジェクトを同じディレクトリに配置する」にチェック**（`.sln` と `.vcxproj` が同じフォルダになる）。
2. チーム用のひな形（`tools/`、`docs/team/`、`.gitignore`、`.gitattributes`、`.github/`、`CLAUDE.md`）を入れる。どちらかの方法で：
   - **Claude Code を使う**（リーダーのPC）：プロジェクトのフォルダで Claude に「チーム制作の環境を作って」と頼む（`team-dev-setup` スキル）。
   - **手で入れる**：今あるチームのリポジトリから、上の6つをコピーする（`tools\team.json` はコピーしない）。

### A-5. リポジトリを作ってルールを設定する（自動）

プロジェクトのフォルダ（`.sln` があるところ）で：

```powershell
cd $HOME\source\repos\<プロジェクトのフォルダ>
.\tools\admin\setup-repo.ps1 -Org <組織名> -Repo <リポジトリ名> -Admins <2人目の管理者> -Members <メンバー1>,<メンバー2>
```

例（このプロジェクトを作ったときのコマンド）：

```powershell
.\tools\admin\setup-repo.ps1 -Org HEWfuwafuwapancake -Repo Proto1 -Admins <2人目の管理者>
```

このスクリプトがやること：

| 手順 | 内容 |
|---|---|
| 1 | 自分がその組織の Owner か、Git の名前とメールが設定されているかを確認 |
| 2 | `tools/team.json`（組織名・リポジトリ名・ブランチ名）を作り、ガイドの `HEWfuwafuwapancake` `Proto1` を実際の名前に置き換える |
| 3 | `git init`、Git LFS の有効化、最初のコミット |
| 4 | GitHub に public リポジトリを作り、`main` と `develop` を置く。既定ブランチを `develop` に、マージ方法をマージコミットだけにする |
| 5 | **Rulesets を4つ作る**（下の表） |
| 6 | 2人目の管理者を Admin、メンバーを Write で招待 |

作られる Rulesets（`https://github.com/<組織名>/<リポジトリ名>/settings/rules` で確認できる）：

| 名前 | 対象 | 内容 | 例外（バイパス） |
|---|---|---|---|
| main と develop は管理者だけがマージ | `main`, `develop` | 削除禁止・強制push禁止・**更新禁止**・プルリクエスト必須 | Admin と組織 Owner が **プルリクエストを通すときだけ** |
| release と hotfix は管理者だけ | `release/**`, `hotfix/**` | 作成・更新・削除を禁止 | Admin と組織 Owner は常に可 |
| メンバーが作れるのは feature だけ | 上記と `feature/**` 以外の全ブランチ | 作成を禁止 | Admin と組織 Owner は常に可 |
| タグは管理者だけ | 全タグ | 作成・更新・削除を禁止 | Admin と組織 Owner は常に可 |

> 管理者でも `develop` / `main` に **直接 push はできない**（プルリクエスト経由のみ）。うっかり事故を防ぐため。

何度実行しても大丈夫なので、ルールを直したときなどにもう一度実行してよい。

### A-6. メンバーを招待する

```powershell
.\tools\admin\add-member.ps1 <ユーザー名>
```

招待したら、メンバーに次の3つを伝える：
- `docs/team/02_メンバー向け_環境構築.md`（GitHub 上でも読める：リポジトリのページ → `docs` → `team`）
- 自分の GitHub ユーザー名を管理者に伝えること
- 招待メールを承認すること

## B. 2人目の管理者：はじめて参加する

（先に「1. PC の準備」を全部やっておく）

1. メールで届く **組織への招待（Owner）** を承認する。メールが見つからなければ https://github.com/orgs/HEWfuwafuwapancake/invitation を開く。
2. プロジェクトを取ってきて設定する：

```powershell
New-Item -ItemType Directory -Force $HOME\source\repos | Out-Null
cd $HOME\source\repos
gh repo clone HEWfuwafuwapancake/Proto1
cd Proto1
.\tools\setup-member.ps1
```

3. 「環境は整っています。」と出れば完了。`tools\admin\` の管理者用スクリプトは、権限を自動で確認して使えるようになる。
4. 確認：`.\tools\admin\add-member.ps1 -List` で自分が `admin` と表示されれば OK。

## D. 管理者の毎日の仕事

管理者も普段の開発はメンバーと同じ（`start-work.ps1` → `save-work.ps1` → `submit-pr.ps1`。使い方はメンバー向けガイドの「9. 毎日の作業」）。
自分のプルリクエストは自分でマージしてよいが、できればもう1人の管理者に見てもらう。

### D-1. プルリクエストを確認して develop にマージする

```powershell
.\tools\admin\merge-pr.ps1            # develop 向けのプルリクエスト一覧
gh pr view 12 --web                   # 12番をブラウザで見る（変更点は Files changed タブ）
gh pr checkout 12                     # 手元に持ってきてビルド・動作確認する
.\tools\admin\merge-pr.ps1 12         # 確認してマージ（feature ブランチも消す）
```

ブラウザの **Merge pull request** ボタンでもよい（管理者には「bypass rules」のチェックが出るので、チェックしてマージ）。
マージしたら **Delete branch** を押してフィーチャーブランチを消す。

確認するポイント：
- ビルドが通るか（`gh pr checkout` して Debug / Release でビルド）
- 新しい `.cpp` / `.h` を追加した PR なら、**`.vcxproj` と `.vcxproj.filters` も変更に入っているか**（入っていないと、マージしても Visual Studio に表示されない。`save-work.ps1` でも止めているが、`-NoProjectCheck` で飛ばされている場合がある）
- 関係ないファイル（`.vs/`、`x64/`、個人設定）が混ざっていないか
- 他の人の作業を壊していないか

### D-2. リリース（提出・発表する版を作る）

```powershell
.\tools\admin\release.ps1 start 1.0    # develop から release/1.0 を作る
# ここではバグ修正・調整だけをコミット＆push（新機能は入れない）
.\tools\admin\release.ps1 finish       # main に入れて v1.0 タグ → develop にも反映 → release/1.0 を削除
```

### D-3. ホットフィックス（提出後の緊急修正）

```powershell
.\tools\admin\hotfix.ps1 start 1.0.1   # main から hotfix/1.0.1 を作る
# 修正をコミット＆push
.\tools\admin\hotfix.ps1 finish        # main に入れて v1.0.1 タグ → develop にも反映 → 削除
```

### D-4. メンバーの追加・確認

```powershell
.\tools\admin\add-member.ps1 kato            # 開発者として招待
.\tools\admin\add-member.ps1 tanaka -Admin   # 管理者として招待
.\tools\admin\add-member.ps1 -List           # 今のメンバーと権限
```

外すとき：リポジトリの **Settings → Collaborators and teams** から Remove。

### D-5. 競合したプルリクエスト

`merge-pr.ps1` が「競合しています」と止まったら、作者に `.\tools\start-work.ps1` を実行してもらう（develop の最新が取り込まれ、競合したファイルが分かる）。直して `save-work.ps1` すれば、プルリクエストが自動で更新される。

## スクリプト一覧

| スクリプト | 誰が | 役割 |
|---|---|---|
| `tools\setup-member.ps1` | 全員（PCごとに1回） | Git 設定・ログイン・LFS・環境チェック |
| `tools\check-env.ps1` | 全員 | 環境チェック（VS / Windows SDK / Git / LFS / gh / 接続先） |
| `tools\fetch-latest.ps1` | 全員 | 作業は始めずに develop の最新を取ってくる（新しく入った PR を一覧表示）。マージ済みのフィーチャーブランチにいたら develop に戻して片付ける |
| `tools\start-work.ps1 <作業名>` | 全員 | フィーチャーブランチを作る・切り替える・develop の最新を取り込む |
| `tools\save-work.ps1 "メモ"` | 全員 | コミットして push |
| `tools\submit-pr.ps1` | 全員 | develop へのプルリクエストを作る |
| `tools\admin\setup-repo.ps1` | 管理者 | リポジトリ作成・ルール設定・招待 |
| `tools\admin\add-member.ps1` | 管理者 | メンバーの招待・一覧 |
| `tools\admin\merge-pr.ps1` | 管理者 | プルリクエストの一覧・マージ |
| `tools\admin\release.ps1` | 管理者 | release ブランチの開始・完了 |
| `tools\admin\hotfix.ps1` | 管理者 | hotfix ブランチの開始・完了 |

`.ps1` を直すときは **BOM付きUTF-8** で保存する（BOM がないと Windows PowerShell 5.1 で日本語が化けて動かない）。
